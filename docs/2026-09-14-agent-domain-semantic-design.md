## 1. 审阅说明与设计结论

本设计使用户能够组合品种、合约月份、Call/Put、方向、行权价和指标进行自然语言查询。例如“2701 对应的铁矿石期权总手数和浮盈”，应由通用筛选、确定性计算与表达能力完成，无需逐题新增工作流。

已有有效持仓、成本、行情和计算服务继续作为事实基础；模型理解请求、选择工具和说明结果。模型不能自行计算业务金额、猜测合约属性或绕过数据权限。

审阅重点是：业务对象和术语是否解释准确、计算和组合范围是否正确、缺数据时的回答是否可接受、案例是否符合预期。接口类型、程序结构和证据路径由工程负责。

## 2. 范围、来源与规则继承

### 2.1 本批支持与边界

【继承】查询范围为服务端确认的宏源授权账户内有效期货和期权持仓，包括未归类持仓。用户指定期权、品种或月份时缩小范围；不能恢复旧版“仅铁矿石期权、八个固定问题”的整体限制，也不能因为数据库有其他账户就开放访问。

## 3. 业务对象、标识与关系

### 3.1 领域边界与责任

【整理】下列边界用于说明业务含义和事实责任，不要求拆成独立微服务，也不把每个技术数据集都称为一个新业务域。

| 业务边界 | 负责的事实与规则 | 提供给本次查询的内容 | 禁止的混用 |
| --- | --- | --- | --- |
| 有效交易事实与持仓 | 成交、开平、来源覆盖、有效剩余数量和成本、事实确认状态 | 指定范围的有效持仓快照及来源；有效平仓事实 | 不将未去重的 WH6 成交和结算持仓直接相加，不把净额视为真实平仓 |
| 市场行情与估值 | 合约市场价格、行情状态、适用规格、确定性估值 | 与持仓快照绑定的估值运行及逐行金额 | 不因价格变化修改持仓数量或确认状态，不用结算价冒充实时价 |
| 历史结算与对账 | 历史结算来源、日期、结算口径及差异 | 已证实的历史事实和明确标注的结算结果 | 历史结算浮盈不是当前浮盈，当前报价不能填补历史缺数 |
| 业务归属与台账 | 基础/战略套保等已确认归属、特殊业务开平和核算 | 已有且适用的标签、归属事实和独立业务口径 | 事实盈亏不等于业务归属盈亏，不能按标签筛选后自动声称已执行台账特殊规则 |
| 持仓分析语义层 | 对上述事实的解释、受控筛选、分组、指标及组合约束 | 本稿定义的 M01–M11 和相关结果 | 不重新裁决上游事实，不生成交易、不推测归属、不新增未定义估值公式 |

业务数据流：有效事实形成持仓快照 → 行情与规格参与估值 → 语义层基于同一快照/估值运行查询和汇总。历史结算及归属通过明确口径提供补充，不直接覆盖当前事实。

【整理】所有权也要清楚：业务负责人决定规则含义与变更；既有事实/行情服务负责权威结果；工程维护映射、校验和版本；模型解释请求和结果。对当前服务缺陷进行标注和修复，不把现有代码自动当作业务真理。

### 3.2 对象目录

【整理，依据 R1–R4】每个对象采用统一定义结构：名称、所属业务责任、业务身份、最小粒度、必要属性、状态、关系及约束、权威来源。下表列基础信息，§3.1、3.3–3.5 补齐责任、粒度和关系；不要求新增同名数据库表。

| 对象 | 业务含义与必要属性 | 标识、关系与约束 |
| --- | --- | --- |
| 授权账户 | 本次允许访问的交易账户 | 使用服务端账户标识；名称是展示值，不能由模型传入身份或扩大权限 |
| 品种 | 如铁矿石；含交易所、品种代码、计量单位 | 名称别名映射到受控目录；同名跨交易所不自行合并 |
| 合约 | 期货或期权的具体交易标的 | 以交易所及规范合约代码识别；不能只用月份作为唯一标识 |
| 期权属性 | 品种、对应月份、Call/Put、行权价、标的合约、实际到期日 | 来自受控规格或经验证解析；月份不等于实际到期日 |
| 有效持仓记录 | 指定快照中某账户、合约和方向的剩余数量及成本 | 沿用事实服务的稳定记录标识；同合约多条来源记录不能直接去重为一条 |
| 持仓快照 | 某一数据状态下的完整有效持仓集合 | 具有不可混淆的结果/版本标识；汇总和下钻引用同一快照 |
| 行情观察 | 某具体合约最新有效市场成交价及时间 | 同一合约可供多条持仓估值；各合约真实成交时间可以不同 |
| 估值结果 | 一条有效持仓与适用行情、乘数及规则的计算结果 | 保留关联持仓、行情时间、估值口径、状态与金额 |
| 归属信息 | 事实记录已有的业务标签或组别 | 可为空；缺标签不排除持仓，不推测策略，历史须有当时证据 |
| 平仓事实 | 已平仓或真实了结记录及其事实盈亏 | 与当前持仓不同；沿用事实服务认定，不因净额计算生成平仓记录 |

核心关系：一个账户拥有多条持仓；一条持仓对应一个具体合约和一个方向；一个合约可以出现在多个持仓记录中；一个快照包含多条持仓；估值通过具体合约关联行情。期权类型、方向和月份分别描述不同属性，不能互相替代。

【继承】事实层处理结算与 WH6 来源覆盖、去重、开平重建；Domain 查询消费处理后的有效结果，不在模型层重复实现 FIFO。

【整理】持仓状态应区分结算确认、临时有效、异常/无法确定和已不在当前持仓中。临时有效可以估值；无法确定的记录不得包装成确定持仓。全部平仓后退出当前数量和浮盈。行情变化只更新估值，不改变持仓事实确认状态。

### 3.3 最小数据粒度与唯一性

“粒度”指一行究竟代表什么。下表是查询合同必须保持的业务约束；键名为逻辑含义，不要求新建同名表。当前代码能证明什么与尚待核验什么分别标注。

| 层级 | 一行代表什么 | 唯一性与计数 | 使用要求 |
| --- | --- | --- | --- |
| 原始来源/剩余批次 | 一份来源中的事实或尚存批次 | 来源身份、版本和记录身份；不是单凭合约唯一 | 由事实层协调；不得与其上层汇总行一起加总 |
| 有效持仓行（本稿计算基粒度） | 一个快照内，某账户、交易所、合约、资产类型、方向的有效剩余数量和成本 | 目标逻辑键：快照身份＋账户身份＋交易所＋规范合约＋资产类型＋方向 | 当前合并代码按交易所/合约/资产类型/方向形成组；账户必须作为外围范围或复合键保留，不用显示名称代替 |
| 合约规格选定结果 | 某合约在本次计算中唯一适用的规格 | 合约身份＋适用规则/版本；本次至多一个有效选择 | 不将同一合约的多个规格版本展开连接到持仓；历史适用性缺失就不声称支持 |
| 行情选定结果 | 某合约在一次估值运行中选定的有效市场观察 | 估值运行身份＋合约身份；至多一个选定观察 | 底层可以有多次报价；先按行情规则选定，再关联持仓 |
| 单行估值 | 某有效持仓行在一次估值运行中的金额与状态 | 估值运行身份＋有效持仓行身份 | 同一持仓多次刷新是不同估值，不可当多条仓位相加 |
| 分析分组 | 用户指定维度组合对应的指标结果 | 原快照/估值运行＋筛选条件＋分组维度及值 | 如 Call/Put 分组、月份分组是同一事实的不同视角，不能混合重复汇总 |
| 平仓事实 | 事实服务认定的有效已了结事实 | 使用事实身份与有效版本，不以日期＋合约自行去重 | M10 使用本层；不是持仓快照中消失一行就自行生成平仓金额 |

【代码证据】`trading_effective_facts.py` 的 `_position_key`、`_baseline_position_items`、`_group_position_items` 表明合约、资产类型、方向在交易所范围内合并，并以数量加权成本；实时推算按账户循环。历史路径会合并各账户基线后调用分组，分组键本身不含账户。因此复合账户唯一性是必须验证的合同，不能宣称历史多账户已安全支持。当前首批宏源范围不因此扩展。

【整理】不假定每一条数据路径都已满足目标粒度：WH6 完整快照、历史基线和推算路径须分别验唯一性。发现同一目标键多行时，先辨别上游合法批次与重复事实；不得在 Agent 层简单去重或盲目相加。必要的正规化由确定性服务在保留来源的前提下完成。

【整理】M07 的“单条”明确为上述有效持仓行，不是原始成交笔或剩余批次。M11 的分母也是查询范围内有效持仓行数，不是源文件行数、工具预览条数或不同合约数。若未满足目标粒度，应标明粒度未核验，不能宣称覆盖率具有跨版本可比性。

### 3.4 关系基数、关联规则与防重复

| 关系 | 本次计算允许的对应数量 | 关联与失败规则 |
| --- | --- | --- |
| 有效持仓 → 账户 | 每行恰好一个授权账户 | 关联前校验身份，缺少或重复身份不推断 |
| 有效持仓 → 合约属性 | 每行一个规范合约；期权必须能确定其适用属性 | 解析和目录冲突时说明影响，不能匹配所有相似代码 |
| 有效持仓 → 选定规格 | 每行零或一个有效选定项 | 无规格时不影响独立数量；影响换算/估值。多候选冲突不能任取一项 |
| 有效持仓 → 选定行情 | 每次估值零或一个有效观察 | 必须先选行情再连接；零项保留数量并标记估值缺失，禁止内连接直接丢持仓 |
| 有效持仓 → 来源证据 | 可以多个来源引用 | 证据多不代表持仓多，不把证据列表展开后求和 |
| 有效持仓 → 归属/标签 | 可能无标签或有多个标签；当前能力须核验 | 可用存在性筛选，不能展开标签后重复金额。跨组可相加须有互斥归属或已批准分配规则；无该规则就标明组有重叠、总计按原始持仓去重集合计算 |
| 估值 → 分析分组 | 可属于多种不同分组视角 | 单一互斥分组内每行一次；不同分组视角的小计不可再合成总体 |

【整理】这些关系是服务内部允许的连接，不授权模型提交任意 join。所有连接前后都应核验有效持仓身份集合、行数及数量是否发生非预期变化；若本应只补属性却使数量翻倍，必须失败，不能交付。

【代码证据】当前 Agent 先按合约字典取行情；规格辅助函数只读取 `is_active=1` 的启用项，Agent 优先取行情中的乘数再取该目录。尚未证明历史规格版本选择、重复启用项及两来源乘数冲突均有保护。实现需核验并保留实际选用依据；对冲突结果暂停相关估值，而不是让模型决定乘数。该工程缺口不代表需要用户重新确认“乘数应来自可靠规格”。

### 3.5 必须保持的业务恒等关系

- INV01：相同完整集合下，M01 = M02 + M03；期权总数 = Call 总数 + Put 总数，仅在类型覆盖完整时成立。
- INV02：Call/Put 的有符号净额 = 卖出 − 买入；输出绝对量和方向，但底层保留符号。净额为零不等于 M01 为零。
- INV03：同一估值运行、同币种、互斥且完整的分组，M08 总额 = 分组金额合计 = M07 行值合计。
- INV04：同一快照行不能因行情、标签、证据或规格多条记录而重复计入。
- INV05：修改展示形式、分页大小或读取顺序不得改变范围和指标结果。
- INV06：缺行情只影响依赖行情的指标；缺期权类型会影响 Call/Put 分类与净额，但不必然影响已证实的总体数量。
- INV07：M11 必须满足 0 ≤ 已估值行数 ≤ 应估值行数；分母为零时显示“不适用”，不显示 100% 或 0% 覆盖率。
- INV08：当前持仓和浮盈在时间轴上不可直接累加；M10 期间累计仅对去重后的有效平仓事实成立。

上述约束是已有公式与完整性原则的可检验表达。若现有代码违反，修复代码或明确局限，不反向修改业务定义使测试通过。

### 5.1 聚合条件

【继承】Call/Put 净额允许在同品种内跨月份抵销数量；按月份、类型、方向的组成仍可追溯。数量净额不表示风险抵销，不引入 Delta 调整。

【整理】先完成授权与筛选，再分组、计算、排序、分页；分页只改变展示，不改变计算集合。不能既统计组小计又统计其明细而重复加总。净额查询必须保留买卖两边；明确“只看卖出的”得到的是卖出持仓，不能仍命名为双边净额。

【整理】跨品种总手数可以表达为机械手数合计，并保留资产/品种范围；不解释为可比较风险规模。净吨数按品种和单位分别输出。金额仅在同币种、同估值口径且覆盖明确时合计；本批不新增汇率转换。

【整理】默认结构化持仓摘要按实际月份、Call/Put、买卖方向组成；用户只问某个总数时只交付该数值及必要限制，不强制附带全部分组。合约级明细保留具体代码，跨方向合计必须有明确标签。

### 5.2 精度与零值

【继承/整理】保留事实层成本均价的原精度，不用界面舍入值重算。沿用现有实时业务函数逐条计算至金额小数两位，再汇总这些行值；同一组的明细和汇总应勾稽一致。本批不变更全系统舍入算法，未来调整须作为独立规则变更核验。

【建议】P3：手数按源数据有效精度显示，整数不补小数；金额默认元、两位小数；吨数保留必要有效位；万吨最多四位小数，小额不得舍成零，必要时同时显示吨/手。用户指定万元或其他展示精度时只改变表达，证据保留原值。

【继承】全部面向用户的时间和时间接口只到秒，使用明确时区。零持仓必须有完整空集合证据；净平可能仍有大量多空持仓；完整估值恰为零才显示零盈亏。缺数据不可转为零。

### 5.4 非可加指标与期间问题

【整理】持仓是存量，成交/平仓是事件流。周一 10 手、周二 12 手不能相加为本周 22 手；两天浮盈 100 元、150 元也不能相加为周收益 250 元。

对于明确“周末持仓”，只使用所要求时点的证据；对于“本周每天持仓”，返回各时点序列，不做合计。缺该时点时可提出已有快照作为带日期参考，但不能偷偷替代。“本周总持仓”没有既定含义时才澄清期末、日均或其他含义；日均/峰值等指标本批未定义，不临时计算。

【整理】成本均价不是可加指标。当前事实服务在相同持仓键内用数量加权；查询不重新改写成本。若未来开放均价汇总，仅在同合约、同方向、同单位等成本可比条件下，按 Σ数量×成本 / Σ数量 计算；不得跨行简单平均。本稿不新增跨合约成本指标。

【整理】类型净额跨月份合并时要合并有符号数量。例如一个月净卖 6 手、另一个月净买 4 手，总体为净卖 2 手，不能加绝对值为 10 手。标签重叠组不满足互斥条件，小计不能用来证明总体。

## 6. 组合查询与连续追问

【整理】一条请求应得到可校验的业务约定：账户授权范围、资产/品种、合约或月份、类型、方向、行权价、时点、所需指标、分组、排序、展示形式。它描述用户目标，不固定唯一工具顺序。

### 6.1 主案例的完整解释

用户：“2701 合约对应的铁矿石期权总手数、浮盈浮亏情况给我说明。”

- 范围：宏源授权范围；品种铁矿石；资产期权；月份 2701；全部 Call/Put、行权价、方向；当前有效快照。
- 指标：M01、M08；缺估值时附 M11 及影响说明。
- 排除：期货 i2701、其他月份、已经平仓的数量；不附加 M10。
- 表达：文字给结论；用户没问净额，不把 M01 替换成 M04/M05。
- 完整性：数量和浮盈分别判断；缺行情不能阻止完整数量交付，局部浮盈不能称全量。

【继承】以上解释已经由用户在本任务确认。它只是筛选与指标组合的一个例子，不建立“2701 专用路由”。

追问中的条件继承、快照刷新和表达偏好属于配套交互约定，见附录 A；本节只定义组合查询的业务含义。

## 7. 价格、时间、来源与生命周期

【继承】实时估值使用具体合约最新有效市场成交价。不是主力连续合约价、标的价、账户自身成交价或结算价。不同合约最后成交时间可能不同，“同一批行情”不等于每个合约在同一秒成交。

【继承】持仓快照固定后，按同一批取得的行情计算分组与合计。持仓版本变化时不得把旧估值贴到新持仓；完整结果至少保留持仓快照、实际数据截至时间（允许未知）、行情时间/状态、规则版本、范围、覆盖和证据。

【继承】临时持仓具备数量、成本、乘数和行情时可估值。新开仓加入；部分平仓只剩余部分贡献浮盈；全部平仓后退出。结算确认改变来源/确认状态，不产生双份持仓。

【继承】行情刷新失败可以沿用此前真实有效成交价，并说明沿用及真实时间；没有有效成交价时不可估值。已到期或异常参考记录不能被包装成当前可正常估值仓位，沿用事实和行情层状态处理，不凭时间自行生成了结事实。

【继承】历史结算查询与当前实时查询分别标注。指定历史日只有持仓结构而无同期行情时，交付结构，浮盈缺失；月末结算价格不能倒推非月末价格。缺某日期数据不能自动跳到最近有数据日期。相对“昨天/上一交易日”按既有交易日规则解析，实际日期在答案中明确。

【整理】若现有工具不支持精确历史时刻，应直接说明支持范围，而不是把日终快照当作该时刻。事件时间、业务交易日、入库时间与查询时间各自保留，夜盘沿用事实层交易日映射。

## 8. 异常与部分结果的业务行为

| 情况 | 可以交付什么 | 不允许的结论 | 状态与依据 |
| --- | --- | --- | --- |
| 持仓完整，全部行情有效 | 完整数量、净额和适用浮盈 | 不超出查询范围 | 【继承】R1/R3 |
| 部分缺行情、成本或乘数 | 独立完整的数量；已估值部分金额与覆盖情况 | 不能称全部浮盈，不能补零 | 【继承】R3 |
| 所有估值条件缺失 | 有证据的数量；说明估值不可用 | 不能显示零浮盈 | 【继承】R3 |
| 相关记录的类型/月份解析失败 | 不依赖该字段的可靠指标；说明目标筛选或净额可能不完整 | 不能把无法分类的行默默排除 | 【整理】完整性原则 |
| 查询范围完整且确实为空 | 无持仓、数量零；未询问时不附加其他指标 | 不能把工具失败当无持仓 | 【继承】R2/R3 |
| Call 买卖数量恰相等 | 净平与仍存在的买卖组成 | 不能说无持仓或无风险 | 【整理】M04/M05 |
| 事实层冲突或重建失败 | 不受影响且可证实的结果，以及异常影响 | 不拿旧基线当当前结果，不由模型裁定事实 | 【继承】R1 |
| 请求精确历史时点但无对应证据 | 说明当前能提供的历史粒度与缺失 | 不用当前行情补历史 | 【继承/整理】R1/R4 |
| 返回结果超过预览/页数 | 全量确定性汇总，明细分批读取或说明未展示范围 | 不把前若干行称为全部 | 【继承】R4/R6 |
| 用户范围超出权限 | 受控说明，不暴露额外账户信息 | 不因自然语言扩大权限 | 【继承】R4 |
| 纯文字答案校验失败 | 有证据的文字部分与缺项说明，必要时明确未完成 | 不自动以表格替代纯文字要求 | 【继承】本任务 |

【整理】数量、净额、分组浮盈、总浮盈的完整性各自计算。一个组缺行情不应使其他组的可靠数量不可见；一个总体状态为部分完成，也不能免除说明具体缺项的责任。

【建议】P5：问“浮亏最多”时先按用户指定粒度计算浮盈，再筛选负值、从小到大排序；同名次并列全部标明。部分估值缺失时只能说“已估值范围内最多”，不能认定全组合排名。

## 附录 A. 交互与展示约定

本附录承接业务语义，不改变指标定义；实现位置属于 Agent 交互、运行及展示层。

### A.1 追问与上下文规则

【建议】P4：同一对话中“其中、这些、刚才、再按……”沿用当前业务范围和快照，只修改明确提出的条件。“只看 Put”将类型改为 Put；“再按行权价拆”增加分组；“改成文字”仅变更表达。

【建议】“再看看 2705”继承当前仍有效的其他条件，并在答案简短标明，例如“沿用刚才只看 Put 的范围，2705……”，避免隐藏筛选。用户说“2705 全部期权”则明确重置类型和方向筛选。

【继承/整理】用户明确“更新到现在、重新查最新”时获取新快照。旧快照失效、权限变化或无法再访问时说明情况，不悄悄把新结果冒充旧结果；允许继续查询时必须标明改用新时点。新对话不继承另一对话的筛选、数字或证据。

【整理】仅修改展示不重新计算；仅在同一快照内追加分组或排序可复用结果。模型识别出的条件也需检查：若漏了月份或指标，不能用一份有证据但范围错误的结果宣布完成。

### A.2 文字与展示约束

【继承】明确的用户展示要求优先；纯文字时既不生成表格视图，也不生成 Markdown 表格。结构化证据存于底层，不能以难以引用为由要求用户使用表格。

【整理】未指定格式的小范围数量/盈亏问题采用简短文字；多组详细对比可以选择列表或表格。该选择不改变指标集合和完整性。只问总手数不附加浮盈；只问浮盈不附加平仓盈亏；整体摘要可以包含用户要求的多个指标。

【继承】“当前持仓浮亏多少”可以返回净浮亏，默认不额外拆毛亏损与盈利抵消。不把事实分组解释成 Gamma、IV 等因果，也不自动给出交易动作建议。

【整理】最终答案必须同时满足：每项必答指标存在或解释缺失、查询范围正确、单位和时点正确、每个业务数字可追溯、展示要求遵循。证据有效只是必要条件；漏掉 Put、错用月份、用表格违反纯文字要求都不算完成。
