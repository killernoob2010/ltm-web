**Tech Stack：** 现有 Python / FastAPI / Pydantic 后端，现有 JavaScript 答案渲染器，pytest 与 Node 内置测试。沿用项目依赖，不新增数据库、第三方包、模型供应商或搜索服务。

## 3. 不可修改的业务合同摘要

以下摘要用于执行时速查，完整定义以 v0.2 对应章节为准；发现两文含义冲突时交主 Agent，禁止自行选择宽松版本。

1. 服务端 Principal 决定宏源授权账户范围，包含未归类有效持仓。模型不能传用户身份或扩账户。筛选在授权集合内执行。
2. 有效持仓目标粒度为“快照、账户、交易所、标准合约、资产类型、方向”。来源批次先按既有事实规则正规化；合法不同批次不能误删，重复来源/行情/标签不能重复加总。
3. “2701 对应铁矿石期权”筛选品种铁矿石、期权、合约月份 2701，包含该月全部类型/方向/行权价；排除 i2701 期货和其他月份。合约月不是统计日期，也不是实际到期日。
4. 总手数是筛选后剩余数量之和。Call/Put 净额分别为卖出减买入；负数表达净买，零表达净平，不能把净平说成无持仓。“卖出的”单边数量不能命名为双边净额。
5. 净额吨数按每行有效乘数计算并保留方向，再合并；万吨除以 10000。不同品种/单位不直接换算合计，跨月不能加净额绝对值。
6. 浮盈采用既有 `calculate_live_position_floating_pnl`，只取本合约有效最新成交价；多头 `(最新价－成本)×数量×乘数`，空头反向，不扣手续费。继承现有有效行两位小数舍入，再加总；不以模型或展示均价重算。
7. “净卖及对应浮盈”给出净额，并明确金额是该类型实际多空持仓合计浮盈；不建立虚构净仓成本。用户明确仅卖出时只算实际卖方；分组要求按所问维度展开。
8. 部分可估值只能输出已估值部分金额及有效行覆盖率。覆盖按计数合并，不能平均百分比；空集合覆盖率不适用。已证实空集合与查询失败严格区分。
9. 行权价范围默认含两端；明确大于/小于则严格比较。先全量筛选和分组计算，再排序、分页；排名需解释并列和部分估值范围。
10. 同一会话追问继承未替换条件；“全部期权”清除此前类型/方向限制。仅换展示复用快照；明确刷新才获取新快照。权限和结果有效期须再次检查。
11. 持仓/浮盈为时点值，不把多日相加为期间持仓/收益。平仓是独立事件流，使用既有事实口径；重叠事件范围去重，绝不与浮盈混成一个总数。
12. 纯文字必须贯穿全链路。只问数量就不超答浮盈。时间展示/API 字段精确到秒。金额和数量仍必须有服务端证据，不能通过删除校验让答案通过。
