## 1. 业务目标

在现有测试版网页中增加一个统一的“Agent 对话”入口。获准测试的用户可以用自然语言询问宏源账户铁矿石期权收盘复盘问题，系统通过 DeepSeek 理解问题，但所有持仓、数量、盈亏、数据状态、证据和业务结论均由确定性程序产生。

合格的 Staging 必须同时具备三类能力：

1. 用户提问后得到针对该问题的回答；
2. 页面主动提示当前可以继续询问的问题；
3. 系统自动生成日常收盘复盘结果。

这三类内容必须在同一个 Agent 页面中清楚区分。未被询问、与当前问题无关或虽同属业务域但并非当前问题所需的内容，不得混入回答正文。

## 2. V1 范围

### 2.1 业务对象

- 账户：固定为系统 canonical account `hongyuan_futures`，页面和 API 不接受用户指定其他账户；
- 页面展示名：宏源账户；
- 品种：大商所铁矿石期权；
- 时间范围：现有结算单能够证明的历史交易日；
- 首轮 Staging 测试资料：用户已授权使用 2026 年 6 月、7 月和 8 月三份整体月结单；
- 数据口径：优先日结单；月结单只回答其能够证明的事实；
- 运行方式：只读问答、解释、自动摘要和测试回放。

### 2.2 明确非目标

V1 不包含以下内容：

- 上海钧能或其他账户、品种和业务域问答；
- 订单融资、贸易台账、天气、新闻或通用知识问答；
- Delta、Gamma、Vega、Theta、IV、Skew 或复杂风险归因；
- 风险阈值、止盈止损、调仓建议和交易建议；
- 对话修改规则、数据、权限或业务归属；
- 自动下单、改单、撤单、平仓、行权、资金划转或任何交易操作；
- 任意 SQL、任意代码执行、任意工具调用或开放式插件；
- 企业微信入口；
- WH6 实时数据或 15:00 最后一笔有效成交价；
- 多 Agent、自动多模型路由、长期跨会话记忆；
- `main`、Production、正式数据库、正式环境变量或正式发布。

用户提出范围外问题时，系统只说明当前支持范围，并在独立推荐区域给出可询问示例；不得凭模型常识继续回答。

## 3. 已确认的八类问题

八类问题是固定目录，不再作为待确认项。自由文本必须被映射为下表之一，无法可靠映射时要求澄清或受控拒绝。

| 编号 | Task Profile | 典型问题 | 必须回答 | 不得附带 |
|---|---|---|---|---|
| Q1 | `option_position_query` | “8 月某日的期权持仓怎么样？” | 实际交易日期、Call/Put 净买卖、按月份/Call-Put/买卖方向的持仓组、必要的数据状态 | 未询问的平仓盈亏、归因或规则长说明 |
| Q2 | `option_previous_trading_day_position` | “昨天的期权持仓怎么样？” | 解析出的上一实际交易日及 Q1 对应持仓结果 | 自行退回最近有数据日期 |
| Q3 | `option_realized_pnl_query` | “这一天实际平仓盈亏是多少？” | 不扣手续费的真实平仓盈亏、实际日期、必要来源和异常提示 | 持仓浮盈亏、完整持仓摘要、未询问归因 |
| Q4 | `option_unrealized_pnl_query` | “这一天持仓浮亏多少？” | 持仓浮盈浮亏、实际日期、估值口径和必要缺数说明 | 真实平仓盈亏、完整持仓摘要、未询问归因 |
| Q5 | `option_pnl_fact_attribution` | “这一天主要是哪几个合约影响？” | 合约组金额、排序、适用时的贡献比例及抵消警告 | Greeks、波动率或主观因果解释 |
| Q6 | `review_data_status_query` | “为什么这份报告不完整？” | 缺失、冲突、来源、影响范围和下一状态 | 用猜测补齐金额或持仓 |
| Q7 | `effective_rule_query` | “现在按什么规则算？” | 指定结果对应的规则、估值口径、计算版本和生效范围 | 修改规则入口或未生效规则 |
| Q8 | `report_evidence_explanation` | “这个数字怎么来的？” | 当前对话中被指代数字的组成、公式、来源和证据引用 | 其他未被指代数字的完整报告 |

Q5 只做事实层归因，即“哪个合约组贡献了多少”。不得把相关性写成波动率、Gamma、期限结构或交易策略方面的因果结论。

## 4. 内容分类与相关性规则

### 4.1 三类允许内容

1. **问题回答**：用户发送问题后生成，只回答当前 Task Profile；
2. **推荐问题**：独立显示在“你可以继续问”区域，不进入回答正文，不计入上下文；
3. **自动结果**：进入每个授权用户自己的“日常复盘”对话，带“自动生成”标签。

### 4.2 回答正文允许的附加信息

除问题本身要求的结果外，只允许自动附加：

- 最终解析出的实际交易日期；
- 数据来源或估值口径；
- 会改变结论可信度的数据缺失、冲突或降级提示。

其他同域信息也视为过度回答。例如用户只问平仓盈亏时，主动附带持仓浮盈亏属于不合格。

### 4.3 相关性目标

- 与当前问题完全无关的内容：0；
- 同域但未被询问的额外业务结果：0；
- 关键数字没有证据：0；
- 数据不足却给确定性结论：0；
- 平仓盈亏和持仓浮盈亏混算：0。

### 4.4 Task-specific Projection

现有 `OptionDailyReviewResponse` 是完整事实合同，不能直接作为每个问题的最终回答。Agent 层必须增加任务投影器：

~~~text
完整确定性结果
      ↓
按 Task Profile 选择必要字段
      ↓
完成校验器检查日期、口径、证据和越界字段
      ↓
固定模板生成最终回答
~~~

投影器是避免过度回答的主要控制，不依赖 Prompt 自觉。

## 5. 数据与计算口径

### 5.1 来源优先级

1. 指定交易日已经确认的日结单；
2. 已确认月结单能够证明的月内成交、平仓事实和月末持仓快照；
3. 系统已有、经过校验并带来源的交易事实；
4. 数据不足时返回部分结果或等待数据，不猜测。

### 5.2 月结单能力边界

月结单通常包含月内成交和平仓明细，但只提供月末持仓和估值快照。因此：

- 月末实际交易日可以验证月末持仓和结算口径持仓浮盈浮亏；
- 月内非月末日期可以回答月结单确实包含的成交和平仓事实；
- 有可靠期初和完整变动时，可以重建结构性持仓，但必须标记为“月结推导”；
- 仅凭月结单不能宣称还原每个交易日的官方持仓估值；
- 缺少当日日结单或可靠历史价格时，非月末持仓浮盈亏必须为空并解释原因；
- “没有足够数据确认持仓”不能写成“当日无持仓”。

### 5.3 盈亏

- 真实平仓盈亏只读取确定性事实字段，V1 不扣手续费；
- 持仓浮盈浮亏按当前 Phase 1 的 `daily_settlement` 口径计算；
- 两类盈亏独立存储、独立展示，任何地方都不得相加成模糊的“总盈亏”；
- 关键金额、数量和贡献必须带 `data_as_of`、来源、计算版本、规则版本、完整性和证据引用；
- 合约乘数来自受控合约规格，模型不能提供或修改。

### 5.4 日期

- 明确日期严格按该日期回答；
- “昨天”解析为当前日期之前的上一实际交易日；
- “今天”不自动退回上一日；
- 明确指定非交易日时，说明该日不是交易日，并可建议相邻有效交易日，但不静默替换；
- 自动任务按中国期货交易日历运行；
- 页面展示所有时间到秒，不显示毫秒、微秒或秒后小数。

## 6. DeepSeek 与确定性核心的职责

### 6.1 DeepSeek 负责

- 把自由文本映射为八个 Task Profile 之一或 `unsupported`；
- 提取显式日期表达；
- 判断是否是对当前会话上一结果的追问；
- 在存在多个可能指代时生成简短澄清问题。

### 6.2 DeepSeek 不负责

- 计算或修改任何金额、数量、日期、持仓和贡献比例；
- 直接查询数据库；
- 自行选择账户；
- 生成 SQL、代码或任意工具参数；
- 决定数据完整性、来源优先级、冲突处理和权限；
- 生成交易建议或执行交易；
- 把原始结算单、整张交易表或其他用户对话作为上下文。

### 6.3 受限意图合同

模型只返回经过 Schema 校验的意图，不直接控制工具：

~~~json
{
  "task_profile": "option_realized_pnl_query",
  "date_expression": "8月27日",
  "reference_mode": "explicit_date",
  "needs_clarification": false,
  "clarification_question": null
}
~~~

允许值必须由服务端枚举。Schema 不合格时最多进行一次格式修复重试，仍不合格即按模型暂不可用处理。

### 6.4 最终回答

V1 最终答案由服务端任务模板根据确定性结果生成。DeepSeek 可以理解用户语言，但不能在最终答案中增加未经投影器批准的数字或业务结论。

推荐问题点击和自动日报已经具有确定的 Task Profile，不需要调用 DeepSeek；模型故障不得阻断这两类确定性流程。

## 7. 会话、追问和保留规则

### 7.1 页面结构

Agent 仍是一个页面、一个对话输入框。页面内部包含：

- 历史对话列表；
- “新建对话”；
- 当前消息时间线；
- 独立的推荐问题区域；
- 一个固定的“日常复盘”系统对话。

窄屏可以把历史列表收进抽屉，但不能变成多个业务问答入口。

### 7.2 新对话

- 新建对话生成新的 `conversation_id`；
- 不继承其他对话的日期、数字、合约组或证据引用；
- “这个数字怎么来的”在没有当前会话锚点时必须要求澄清；
- 用户之间、不同会话之间严禁共享上下文。

### 7.3 老对话

- 用户打开自己的历史对话后，可以继续追问；
- 服务端只加载同一用户、同一 Web 渠道、同一会话的上下文；
- 权限在每次请求和每次确定性工具调用前重新校验，历史访问权不代表当前仍有权限。

### 7.4 模型上下文

每次自由文本提问最多向 DeepSeek发送：

- 当前用户问题；
- 当前会话最近 6 轮用户—系统交流，共最多 12 条可用消息；
- 最近一次成功业务任务的结构化锚点：Task Profile、实际日期、被展示指标名称、结果引用；
- 支持的八类问题定义和输出 Schema。

推荐问题、加载提示、错误状态和其他会话内容不进入模型上下文。关键数字每轮重新从确定性工具读取，不能从聊天文字中复用为事实。

### 7.5 自动结果会话

- 每个授权用户拥有独立的“日常复盘”对话；
- 自动结果带 `automatic_result` 类型和“自动生成”标签；
- 自动结果不插入用户正在进行的普通对话；
- 用户可在“日常复盘”对话中继续追问该结果；
- 后续数据补齐生成新消息，旧消息标记“已被更新”并链接到新结果，不静默覆盖。

### 7.6 保留期限

- 普通对话和消息正文在线保留 90 天；
- 90 天后正文和结构化回答内容被清除或不可恢复地脱敏，列表不再展示该对话；
- 脱敏任务元数据、状态、版本、耗时秒数和错误分类保留 12 个月；
- 现有操作日志继续遵循项目既有 12 个月在线归档合同；
- 清理由幂等任务执行，不能因重复运行误删未到期内容。

## 8. 超时、重试和降级

### 8.1 DeepSeek 请求

- 单次最长 15 秒；
- 仅对连接超时、读取超时、429 或 5xx 自动重试一次；
- 两次总等待不超过 30 秒；
- 同一个 `client_request_id` 和任务编号贯穿重试；
- 不对 4xx 参数/认证错误盲目重试；
- 结构化输出不合格最多修复一次，计入同一重试预算。

### 8.2 两次失败

- 用户问题已经保存，不丢失；
- 返回受控状态 `temporarily_unavailable`；
- 页面显示“Agent 暂时无法理解该问题，请稍后重试”；
- 不调用错误推断出的业务工具；
- 不生成猜测性回答；
- 自动日报和推荐问题点击继续走确定性流程。

### 8.3 幂等

前端每次发送生成唯一 `client_request_id`。服务端按用户和该编号去重：

- 浏览器重复点击、网络重发或一次模型重试不能生成重复用户消息；
- 已完成请求重复提交时返回原任务和原回答；
- 正在处理的重复提交返回同一任务状态，不并行启动第二次模型调用。

## 9. 数据缺失、冲突和补齐

| 状态 | 条件 | 用户结果 |
|---|---|---|
| `complete` | 当前问题需要的数据和证据全部满足 | 正常回答 |
| `partial` | 一部分事实可证明，另一部分缺少 | 只回答可证明部分，列明不可回答项 |
| `waiting_for_data` | 指定日期必要结算单或事实尚未到达 | 保留原日期，说明等待什么，不替换日期 |
| `data_anomaly` | 来源冲突、勾稽失败或关键证据不一致 | 受影响金额为空，保留冲突并等待人工 |
| `needs_clarification` | 日期或追问对象无法唯一确定 | 只提出一个必要澄清问题 |
| `unsupported` | 超出八类任务或业务域 | 说明 V1 能力边界 |
| `temporarily_unavailable` | DeepSeek 两次失败且无法解析自由文本 | 保存问题并提示稍后重试 |

严禁以下转换：

- 缺失值转成 0；
- 缺日结单转成“无持仓”；
- 冲突来源自动选边；
- 指定日期自动替换为最近可用日期；
- 用月末估值倒推非月末官方持仓浮盈亏；
- 数据补齐后静默修改旧消息。

## 10. 自动日常结果

### 10.1 业务时间

- 每个实际交易日北京时间 15:05 进入到期检查；
- 当前数据阶段生成“上一个实际交易日”的结果；
- 自动结果固定包含数据就绪/完整性状态和简洁期权收盘摘要；在数据允许时分别列示持仓概况、真实平仓盈亏与持仓浮盈浮亏，这一固定日报结构不受单项问答的投影限制；
- 周末和节假日不产生新的计划任务；
- 日结单未到时生成 `waiting_for_data` 自动结果；
- 数据后续导入后，按原目标日期补生成并标记旧消息已更新。

### 10.2 Staging 运行方式

当前 Render Staging 可能休眠，因此采用两层触发：

1. 实例在线时，由进程内调度器检查 15:05 到期任务；
2. 实例启动、唤醒或授权用户打开 Agent 页面时，执行一次幂等补跑检查。

如果实例在 15:05 休眠，报告在首次唤醒时补跑，并同时记录计划时间和实际生成时间。Staging 不宣称具备持续在线环境的严格准点保证。

精确墙钟级生产调度、付费 Cron 或外部调度服务属于 Production 前的单独决策，不在本轮范围内。

### 10.3 历史回放

为使用 6、7、8 月月结单验收自动结果，提供仅管理员可调用、仅 Staging 可启用的历史回放接口：

- 明确传入一个历史交易日期；
- 运行与自动任务完全相同的确定性流程；
- 结果进入授权用户的“日常复盘”对话；
- 相同用户、日期、来源版本和计算版本不得重复生成；
- Production 默认禁用并返回 404；
- 普通用户页面不展示回放控制。

历史回放用于验证同一业务链路，但不得描述成系统已经在历史日期真实准点运行。

## 11. 权限

### 11.1 可使用人员

Staging 首轮仅允许：

- 管理员角色；
- 王景泽对应的唯一系统用户 ID；
- 需求方本人指定的唯一测试用户 ID。

以上集合按唯一用户 ID 去重；如果其中某个指定账号本身已经是管理员，不再重复创建或授权另一个账号。如果两个指定身份在 Staging 用户表中不能唯一识别，接手模型必须停在授权写入之前，只报告需要确认的冲突账号；不得按相似姓名猜测。

### 11.2 技术规则

- 新增专属模块权限 `closing_review_agent`；
- 普通用户、领导、部门默认权限和访客权限均为关闭；
- 管理员按现有管理员规则拥有权限；
- 指定身份中不属于管理员角色的测试账号必须通过唯一用户 ID 显式授权；
- 使用 Agent 还需通过现有 `trading.options:view` 权限；
- 无权限时菜单不可见，直接调用 API 返回 403；
- 权限校验发生在模型调用和交易数据读取之前；
- 不返回“该账户存在但你无权限”等侧信道信息；
- 自动结果只投递到当时仍有双重权限的用户会话。

## 12. 页面要求

### 12.1 入口

- 在现有 SPA 中新增一个一级业务分组“智能助手”，其下只有一个菜单“Agent 对话”；
- 不创建独立站点，不拆成八个菜单；
- 复用现有登录、权限菜单和整体视觉语言；
- 前端建议拆为 `frontend/closing_review_agent.js` 和 `frontend/closing_review_agent.css`，避免继续扩大主 `app.js`。

### 12.2 对话页

桌面端包含左侧历史列表和右侧对话区；移动端历史列表可折叠。对话区必须包含：

- 新建对话按钮；
- 当前对话标题；
- 消息时间线；
- 自动生成、部分结果、等待数据和异常标签；
- 独立的“你可以继续问”推荐区域；
- 单一文本输入框和发送按钮；
- 发送中状态；
- 重试入口，但重试沿用原问题并生成新的 `client_request_id`。

### 12.3 安全显示

- 所有模型和用户文本按纯文本渲染，不直接注入 `innerHTML`；
- 不显示 DeepSeek API Key、内部 Prompt、原始结算单、数据库字段或账户编号；
- 证据引用显示为用户可理解的来源和数据日期，不暴露内部敏感路径；
- 页面时间只到秒。

## 13. 后端接口合同

建议前缀统一为 `/api/closing-review-agent`：

| 方法与路径 | 用途 | 权限 |
|---|---|---|
| `GET /conversations` | 游标分页读取当前用户 90 天内对话 | Agent + options view |
| `POST /conversations` | 新建普通对话 | Agent + options view |
| `GET /conversations/{id}/messages` | 游标分页读取自己的消息 | Agent + options view + owner |
| `GET /suggestions` | 读取固定或上下文相关推荐问题 | Agent + options view |
| `POST /conversations/{id}/messages` | 发送自由文本或已知推荐问题 | Agent + options view + owner |
| `POST /admin/replay` | Staging 历史自动结果回放 | 管理员 + Staging 开关 |

接口约束：

- V1 使用一次请求返回一个完整业务状态，不实现 SSE、WebSocket 或逐字流式输出；页面在最长 30 秒处理窗口内显示发送中状态；
- `conversation_id` 必须属于当前用户；
- 普通消息正文去除首尾空格后长度为 1—1000 个字符；
- `client_request_id` 必填，采用 UUID 字符串；
- 推荐问题通过受控 `suggestion_id` 提交，不接受前端指定 Task Profile；
- API 不接受账户 ID、SQL、工具名、模型名或 Prompt；
- `partial`、`waiting_for_data`、`data_anomaly`、`needs_clarification`、`unsupported` 和 `temporarily_unavailable` 都是已处理业务状态，首次处理完成时返回 200 和结构化消息；
- 重复请求命中仍在处理的同一任务时返回 202 和该任务状态，不启动第二个任务；
- 未认证返回 401，无权限返回 403，不属于当前用户的会话统一返回 404；
- 意外服务错误才返回 5xx。

## 14. 持久化与审计

新增专属表，不把完整对话正文塞入通用操作日志：

### 14.1 `closing_review_conversations`

保存用户、渠道、普通/日常复盘类型、标题、系统键、状态和最后消息时间。每个用户只能有一条 `daily_review` 系统对话。

### 14.2 `closing_review_messages`

保存会话、任务、角色、消息类型、纯文本正文、受控结构化展示数据、状态、被哪个新消息替代、创建时间和脱敏时间。

### 14.3 `closing_review_tasks`

保存用户、会话、请求幂等键、任务类型、Task Profile、目标日期、状态、已经校验的意图、最小结果投影、供应商/模型标识、脱敏用量、结束原因、模型耗时秒数、Prompt/Workflow/计算/规则版本、重试次数、错误分类、来源签名和开始/结束时间。

禁止保存：

- DeepSeek API Key；
- 数据库连接串；
- 完整系统 Prompt；
- 模型未校验的原始长响应；
- 原始结算单正文；
- 其他用户对话；
- 任意交易凭据。

通用 `operation_logs` 只记录简短生命周期事件，例如新建会话、回答完成、模型超时、自动补跑和权限变更，不记录完整问答正文。

## 15. 推荐问题

推荐问题不是模型自由生成，采用版本化白名单。空对话默认至少展示：

- 查询指定日期的期权持仓；
- 查询指定日期的真实平仓盈亏；
- 查询指定日期的持仓浮盈浮亏；
- 查看某份结果为什么不完整。

完成一条回答后，可以根据当前结果显示最多 4 条追问，例如：

- “这个数字怎么来的？”
- “主要是哪几个合约影响？”
- “这份结果按什么规则计算？”
- “为什么这份结果不完整？”

只有当前结果确实支持时才显示相应追问。推荐区域不写入消息表、不进入模型上下文，也不能包含未授权账户或未实现能力。

## 16. Completion Validator

任何回答保存为成功前必须检查：

- 用户、会话、Agent 权限和 options view 权限仍有效；
- Task Profile 在白名单内；
- 实际交易日期已解析且可展示，或状态明确为需要澄清；
- 所有关键数字来自确定性结果；
- 当前任务要求的数字带证据；
- 平仓盈亏和持仓浮盈亏没有混算；
- 投影中没有超出当前任务允许的业务字段；
- `partial`、`waiting_for_data` 和 `data_anomaly` 没有确定性伪结论；
- 最终文本与结构化投影一致；
- 没有交易动作、任意工具或其他业务域内容；
- 用户可见时间精度不超过秒。

任一关键检查失败，任务不能标记 `succeeded`，而应变成相应的受控状态或内部失败。

## 19. 首轮真实页面问题样本

开发模型先在 Staging 运行以下代表场景，日期使用导入后识别出的真实交易日，不硬编码示例日期：

1. 分别询问 6、7、8 月月结单记录的实际月末交易日持仓；
2. 只问其中一天的真实平仓盈亏；
3. 只问其中一天的持仓浮盈浮亏；
4. 在同一对话追问“这个数字怎么来的？”；
5. 在同一对话追问“主要是哪几个合约影响？”；
6. 新建对话后直接问“这个数字怎么来的？”，预期要求澄清；
7. 查询一个月内非月末日期，预期按证据返回完整或部分结果；
8. 查询一个没有对应结算单的日期，预期等待数据；
9. 询问下单或其他业务域，预期受控拒绝；
10. 触发一次历史自动结果回放，验证“日常复盘”对话和“自动生成”标签。

用户后续会亲自扩大真实页面提问量；开发模型不得把上述有限抽检描述成用户已经完成最终业务验收。

## 20. Gate A 评估

### 20.1 D/T/R/C

- **D3**：改动属于单一“收盘交易复盘 Agent”业务模块，涵盖其权限、会话、模型适配、Workflow、调度、API 和 UI；没有连接两个独立业务域，也没有形成系统级共享 Agent 平台。
- **T3**：验收覆盖结算单事实 → 确定性计算 → Agent 路由/存储 → DeepSeek → API → 真实 Staging 页面的一条模块内集成链；不包含跨业务域或 Production 端到端流程。
- **R3**：涉及金融事实、权限、外部模型、会话数据和 Staging 新表，必须执行数据库备份、权限负向测试和真实页面验收。
- **C1**：默认由一个新的主开发模型执行，不创建子 Agent。用户仅表示稍后交给新模型，不等于授权多 Agent。

反证：虽然包含前后端、数据库、模型和调度等多个技术层，但它们服务于同一个业务模块，因此不是 D4/T4。

### 20.2 影响测试宽度

测试范围为 `whole_module`：新 Agent 模块的八类问题、权限、会话、模型、调度、存储和真实页面都需覆盖。现有交易管理、结算单导入、登录权限和页面启动执行直接影响回归；订单融资、贸易台账、风险预警、行情和研究模块保持不变，只做最小页面启动与全量自动化回归，不重新验收其业务功能。

- PostgreSQL 新表启用 RLS，并撤销 `anon` / `authenticated` 直接权限；
- 页面只通过 FastAPI 访问，不能直连 Supabase Data API；
- 不修改既有交易事实表语义；
- Production 不执行迁移。

### 22.3 回滚

- 代码回滚点：接手开发时重新确认的 `origin/staging` 基线；本文件形成时的参考值是 `4eca33c`；
- 首选回滚：关闭 `CLOSING_REVIEW_AGENT_ENABLED` 和自动调度开关，重新部署基线提交；
- 新 Agent 表可以留在 Staging 且不再被读取，避免为了回滚执行破坏性删除；
- 如必须删除或恢复表，使用变更前备份并另行确认明确目标；
- DeepSeek Key 从 Staging Secret 移除属于回滚的一部分，但不得在日志或文档记录其值。

## 23. 外部前提与阻塞条件

真实 DeepSeek 验收需要 Staging 服务端具备有效 API Key。代码、Fake Adapter 和本地测试可以在没有 Key 时完成，但以下条件任一成立时，不得宣称合格 Staging：

- Staging 没有有效 DeepSeek API Key；
- DeepSeek 当前官方接口或模型配置无法通过最小真实调用；
- 两个指定测试身份不能在 Staging 中唯一映射；
- Staging 数据库目标不明确或备份失败；
- 三份月结单不能通过现有预检；
- 需要付费外部调度服务才能达到新的验收要求；
- 实现需要进入 Production、交易执行或其他业务域。

发生阻塞时，只报告具体缺口、影响和解锁条件，不以 Mock、API 200 或本地页面代替。

## 24. 完成定义

只有同时满足以下条件，开发模型才可以报告“Agent V1 Staging 已完成”：

1. `AR-001`—`AR-016` 均有实现、自动化和所需真实表面证据；
2. `AC-001`—`AC-043` 全部通过，或确实不适用的项目有经用户确认的书面原因；
3. 三份授权月结单已在 Staging 通过真实导入和回读；
4. Staging 使用真实 DeepSeek，而非 Fake/Mock；
5. 管理员和两个指定测试身份对应的账号可以使用，其他用户无法使用；
6. 问题回答、推荐问题、自动结果同时存在且清楚区分；
7. 真实页面抽检中过度回答、无关内容、无证据关键数字和越权均为 0；
8. 自动化回归通过，真实 Staging 页面无阻断错误；
9. Staging 提交、数据库影响、Secret 状态、已知限制和回滚点已记录；
10. `main` 和 Production 未变化；
11. 用户尚未亲自扩大测试时，状态应写“Staging 已交付，等待用户验收”，不能写“正式完成”或“Production 完成”。
