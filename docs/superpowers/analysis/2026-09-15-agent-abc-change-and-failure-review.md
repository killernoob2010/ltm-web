## 六、根因：从问题输入到空答案

### G1：服务端没有真正拥有日期解释权（已由代码与离线复现确认）

- `planner.py:70 apply_time_windows` 遇到非空 time_window 直接保留，模型可自填 default/user/inherited 来源标签。
- `validate_plan` 校验字段/类型/来源能力，没有拿当前问题和可信历史核实日期来源。新规划输入也没有显式业务时钟字段。
- 同一个函数还把中文“当前持仓”缺省补成最近14天，混淆“最新快照”和“期间数据”。因此仅补一条“不要2024”的提示仍不够。
- 离线复现：2024范围经过 apply_time_windows 和 validate_plan 后原样保留；去掉模型日期后又得到2026-09-02至2026-09-15，仍不是持仓 latest。

### G2：错误时间窗在覆盖层放大为“范围、指标都缺失”（已确认）

- `coverage.py:287 _expected_scope` 不分目标类型，将 requirement.time_window 塞进 start_date/end_date。
- 实际持仓 envelope 是 asset_type=option、option_type=call/put、as_of=latest，没有期间起止日。
- `_scope_matches` 因日期不存在而排除结果；随后指标检查只看匹配后的集合，所以连已存在的 net_quantity 也被报为缺失。
- 使用相同结构的合成 ToolEnvelope 复现：含2024时间窗 → scope_mismatch + metric.net_quantity；仅删除该窗 → scope_matches=True、missing_codes=[]。
- 因而不能把所有 metric.* 错误解释成“数据库确实没该数字”；必须区分无数据与被错误范围排除。

### G3：旧规划规则与用户的指标限制冲突（已确认）

- `planner.py:61` 明文要求遇到“净买 Call 与净卖 Put”同时请求 gross数量、净额、实际浮盈。
- 用户此题只要数量。模型扩展指标不是完全无来由，而是受到这条强制指令驱动。
- 额外“比较月份分布”是计划中实际存在的扩展；尚不能指认某一行硬编码直接导致它，但 validate_plan 没有检测该需求缺少用户依据。
- 工具结果的浮盈不可用不能自动阻断用户只问数量的需求；模型此题虽然把工具 required_metrics 收窄为数量，仍无法与扩展后的计划一致。

### G4：切换 SDK 时只接了结构类型，遗漏了项目引用协议（代码缺口已确认；具体错误拼法未知）

- 旧 `prompts.py` 明确规定正文 `{{fact:UUID#/metrics/name}}`、行/分组引用、blocks.refs、公开正文引用及不可用数值规则。
- 新 `pydantic_runtime.py:506` 只告知“绑定精确 result_ref”，没有复用完整规则；`AnswerBlock.text/refs` 只是普通字符串，JSON类型校验不会验证内部引用语法。
- 离线演示：正确占位符和末尾多加 `/value` 的占位符都能通过 ModelAnswer21 结构校验，只有前者能通过事实解析器。这是“结构化输出合法≠业务引用合法”的具体例子。
- #137 真实记录明确五处 invalid_reference；原始草稿未保存，不能断言它一定是 `/value`、裸 UUID 或另一种错误。示例只证明同类故障机制。

### G5：修正反馈链漏掉最关键的底层错误（已由离线复现确认）

- `answer_v21` 把 invalid_reference 放在 limitations，保留受影响片段 ID。
- `delivery_gate.py` 构造 validation_summary.unresolved_codes 时只汇总覆盖报告和高层交付错误，没有合入底层 limitations 的安全错误码。
- `_repair_feedback` 只读上述摘要/覆盖报告，没有读取 limitations；即使白名单已经有 invalid_reference，实际也拿不到。
- 离线复现：limitations 含 invalid_reference，最终摘要与修正反馈均不含它，只剩 answer_delivery_partial/delivery_quality_check_failed 等。
- 即使修正器修好了语法，也被禁止重做计划或取数，不能消除2024计划与latest结果的冲突。因此应先保证计划正确，再使用一次答案修正。

### G6：时间通过状态有旁支误报风险（本轮新增发现，非空答案直接原因）

- `coverage.py:485` 用“存在候选结果”决定 time_status=observed；`delivery_gate._check_time` 再据此判通过。
- 离线合成结果未给 data_as_of，只给 captured_at，仍被记为 observed。
- 修复 G1/G2 后不能简单把这项当时间验收通过。必须区分查阅时间、源数据截至时间、用户请求范围；缺失时明确未知，不拿 captured_at 代替。

### 整体因果链

用户只问当前数量 → 规划强制加入额外指标并接受无依据日期 → 执行工具查的是最新持仓 → 覆盖层按错误期间排除证据 → 模型缺少精确引用规则，事实片段被删除 → 修正反馈又缺底层语法错误且无法修计划 → 空正文、failed。

保护性门禁拦住未核验答案是合理的；需要修正门禁上游输入和诊断传递，不能通过删校验、强制complete或直接展示未核实数字“修好”。

## 七、为什么本地测试没有提前发现

1. `test_pydantic_runtime.py` 的 ScriptedSDK 按调用次数返回预写计划/工具/答案；引用是测试作者直接写正确的，不依赖模型阅读提示词。
2. 该主链样本 time_requirement 写英文 latest；近期识别正则主要是中文，所以没有触发真实“当前持仓”的14天默认逻辑。
3. R6返修测试证明某些诊断可传递，没有覆盖“底层limitations → 最终summary → repair prompt”全部错误类别。
4. 字段投影测试证明模型看得到来源/分组，不证明其能正确选择期间、净买净卖语义和引用语法。
