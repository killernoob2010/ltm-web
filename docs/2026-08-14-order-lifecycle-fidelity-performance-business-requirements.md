## 2. 业务结论

当前测试版已经具备订单全流程管理的主要功能能力，包括来源状态、汇总、字段搜索、多选筛选、业务卡片、分页、业务详情、主卡编辑、子记录编辑、人工 FCR 和审计信息等。

本轮问题不是业务功能缺失，而是以下三类交付偏差：

1. 已确认原型没有被当作直接实施基准，导致页面结构、卡片布局、风险表现、详情交互和编辑方式与原型存在明显差异。
2. 列表接口在分页前展开全部匹配业务的完整子记录，产生随业务数量线性增长的重复查询，造成页面加载缓慢。
3. 新解析规则已经停止生成“钢厂 + 行号”临时编号，但 Staging 仍保留旧规则产生的历史业务卡，导致页面继续出现“北满-17”等非权威编号。

因此，本轮应按“功能规则保持不变、页面按原型还原、数据库先聚合分页、详情按需加载、旧编号受控治理”的路线修改。

## 3. 业务目标

本轮修改需要实现以下目标：

1. 保留当前已经完成的全部业务功能和业务计算规则。
2. 保留系统现有左侧导航、顶部用户区和统一应用外壳。
3. 将订单全流程管理右侧工作区按冻结原型恢复，不再使用信息等价但结构不同的通用卡片替代原型组件。
4. 增加业务规模汇总，使用户进入页面后立即看到存续业务、其中进行中业务和已完结业务数量。
5. 解决筛选文字截断、文字越界、控件尺寸不一致和清空按钮失衡问题。
6. 恢复宽业务卡、字段级风险背景、固定下一步区域和融资/执行/到期回款的信息层级。
7. 恢复整页详情、顶部横向 01–08 八段导航、逐条明细表和统一编辑全部字段交互。
8. 将列表查询从“全部业务完整展开后分页”改为“数据库筛选、聚合、排序和分页后只加载当前页”。
9. 使列表查询量不再随全部匹配业务数量按每笔业务重复增长。
10. 禁止新导入生成钢厂加行号的临时业务编号，并对 Staging 旧编号做可追溯、可回滚的受控治理。
11. 通过自动化结构契约、性能行为测试和原型并排截图验收，防止页面再次在功能正确的情况下偏离已确认原型。

冻结原型的 HTML、CSS、JavaScript 和最终截图是本轮页面结构、组件、字段顺序和交互的直接实施基准，不是视觉参考或灵感来源。

实施时必须先建立原型与现有页面的区块映射，再逐区块还原。不得以“现有通用组件信息等价”为理由替换原型的搜索区、筛选区、宽卡、风险事实框、详情侧栏、明细表或统一编辑态。

### 5.2 明确允许的差异

- 系统左侧导航继续使用当前统一导航，不复制原型中的静态演示导航数据。
- 用户身份、权限和退出操作继续复用现有系统机制。
- 原型中的演示业务数据必须替换为 Staging 当前真实可见业务数据。
- 当前来源没有提供的字段显示“待来源回读”或明确空状态，不虚构内容。
- 后端接口和数据库内部实现可按性能要求调整，但不得改变页面业务语义。
- 页面只验收电脑端，不增加移动端适配范围。

未在本节列出的差异默认视为待修复偏差。

## 6. 页面信息架构

主列表从上到下固定为：

1. 页面标题和面包屑；
2. WPS 与邮件台账最近成功获取时间；
3. 三项业务规模汇总；
4. 六项运营指标；
5. 精确字段搜索；
6. 常驻筛选；
7. 当前筛选状态与清空筛选；
8. 总览 / 本周关注重点视图切换；

## 7. 顶部汇总与统计口径

### 7.1 三项业务规模汇总

本稿采用以下推荐口径，作为业务审核重点：

1. **存续业务**：来源有效且状态不属于“已完结”或“已结算”的全部业务主卡。
2. **其中进行中**：存续业务中已经进入明确业务节点、当前状态不是“待确认”的业务主卡。
3. **已完结业务**：融资业务状态为“已完结”，或过单业务状态为“已结算”的业务主卡。

“其中进行中”是“存续业务”的子集，不与存续业务互斥。页面必须使用“其中进行中”文案，避免用户将三个数字误认为可以直接相加。

### 7.2 六项运营指标

三项业务规模汇总下方保留以下运营指标：

1. 存续融资金额；
2. 高风险；
3. 中风险；
4. 低风险；
5. 数据异常；
6. 更新异常。

原七项指标中的“已完结”移入三项业务规模汇总，不在运营指标中重复展示。

### 7.3 汇总共同规则

- 汇总服从当前字段搜索、筛选条件和总览 / 本周关注重点视图。
- 汇总按全部匹配结果统计，不受当前分页影响。
- 已完结或已结算业务不得继续计入高、中、低风险数量。
- 存续融资金额只统计未完成还款的融资余额，不重复累计已还融资。
- 更新异常按 WPS 和邮件台账当前有效同步错误来源计数。
- 数据异常按业务卡去重计数，不按异常行数累计。
- 真实结果为 0 时显示 0；尚未加载或请求失败时不得显示为业务上的 0。

## 8. 精确搜索

### 8.1 搜索字段

字段选择固定支持：

- 业务编号；
- 合同号；
- 贸易主体；
- 供应钢厂；
- 终端客户；
- 货物品名；
- 融资银行；
- 日期；
- 金额。

### 8.2 搜索交互

- 搜索区独占一行，由字段选择、输入框和主按钮“搜索”组成。
- 搜索按钮占据剩余宽度，并与输入控件等高。
- 按 Enter 与点击搜索按钮结果一致。
- 修改输入内容但未提交时，当前结果仍标注原已应用搜索条件。
- 提交新搜索条件后回到第一页。
- 空关键词提交等同于清除关键词，但不清除其它筛选。
- 搜索、筛选、视图、页码和每页条数在同一登录会话内保留。

### 8.3 搜索规范化

- 业务编号和合同号统一处理空格、大小写、半角横杠、全角横杠和长横线。
- 日期按明确日期值匹配，不将任意数字模糊匹配为日期。
- 金额支持原币金额和页面展示单位对应匹配，不能因千分位或小数格式不同漏查。
- 搜索不得绕过当前用户权限或返回无权查看的业务。

## 9. 常驻筛选

### 9.1 筛选组

筛选区固定展示：

- 业务类型：融资类业务、过单类业务；
- 风险等级：高风险、中风险、低风险；
- 异常类型：字段缺失、来源冲突、节点矛盾、未来日期、无异常；
- FCR：FCR、非 FCR；
- 业务状态：已放款、已集港、已装船、已交单、待收汇、订单执行中、已回款、已结算、已完结、待确认。

### 9.2 筛选逻辑

- 同一筛选组内为 OR；不同筛选组之间为 AND。
- 业务类型、风险、异常和状态组提供独立全选 / 全不选。
- FCR 只显示 FCR / 非 FCR，不显示全选或全不选按钮。
- 任一组全不选时结果为空，并明确显示空状态。
- 清空筛选恢复全部默认选中、清空关键词、切回总览并回到第一页。
- 条件变化时旧请求不得覆盖最后一次选择。

### 9.3 布局和溢出

- 筛选组使用确定的桌面网格，不依赖内容自然挤压形成布局。
- 控件文字不得被截断、溢出边框或覆盖相邻控件。
- 全选、全不选、筛选选项和清空按钮使用统一高度、字号、边框和圆角。
- 业务状态独占稳定的一行或完整网格，不折叠，不横向溢出。
- 清空按钮放在筛选底部操作区，不与最后一个筛选组竞争宽度。

## 10. 总览与本周关注重点

- 视图切换位于筛选面板下方、业务卡片上方。
- 默认选择“总览”。
- 总览显示全部当前匹配业务。
- 本周关注重点继续使用当前已确认业务规则，不在本轮修改关注重点口径。
- 两种视图继续服从字段搜索和全部筛选条件。
- 切换视图后回到第一页。
- 当前选中视图必须具有清晰的下划线、颜色或背景状态。
- 页面重新进入或从详情返回时恢复原视图、筛选、页码和滚动位置。

## 11. 业务主卡

### 11.1 卡片总体结构

每张业务卡采用横向宽卡，固定由以下部分组成：

1. 顶部标签与业务身份；
2. 融资 / 资金摘要；
3. 执行事实与风险来源；
4. 到期、回款和银行还款；
5. 底部下一步和详情入口。

不得继续使用当前多个等权小方格拼装成业务卡的方式。

### 11.2 顶部业务身份

- 融资主卡类型标签显示“融资类业务”；过单主卡使用短标签“过单”，并通过可访问文本保留完整分类“过单类业务”。
- 当前状态使用深色状态标签，正文不重复显示相同状态。
- 显示当前最高风险标签。
- FCR 只在人工已勾选时显示。
- 存在异常时显示异常数量标签。
- 业务编号使用最大字号，并且只能显示权威业务编号。
- 合同号、贸易主体、供应钢厂、品名和终端客户按原型顺序展示。

### 11.3 融资类业务卡

融资类业务卡至少展示：

- 贷款行；
- 存续融资金额；
- 融资笔数；
- 放款完成情况；
- 集港状态；
- 装船状态；
- 交单状态；
- 当前到期日；
- 剩余或逾期天数；
- 展期天数；
- 客户回款进度；
- 银行还款进度；
- 下一步。

### 11.4 过单类业务卡

- 不显示融资金额、贷款行、融资笔数、到期日、展期或银行还款区域。
- 展示业务身份、合同、执行事实、客户回款、结算状态、风险原因和下一步。
- 不使用空融资方格占位。

### 11.5 字段级风险

- 卡片顶部风险标签表示业务整体最高风险。
- 具体风险落在对应事实框背景：高风险使用浅红背景，中风险使用浅黄背景。
- 风险事实框内不重复显示“高风险 / 中风险”文字。
- 不能仅依赖左侧边线或红色文字表达风险。
- 无风险字段保持普通背景，不因整卡最高风险而全部染色。

### 11.6 下一步

- 每张卡只展示一条明确的下一步。
- 下一步固定放在卡片底部，使用稳定的视觉区域。
- 数据异常可触发“人工判断并修正数据异常”，但详情仍需保留原业务节点和异常原因，不能丢失业务上下文。
- 已完结或已结算业务显示“无”或明确完成状态，不生成虚假待办。

## 12. 整页详情与编辑交互

### 12.1 详情头部

- 顶部提供固定“返回主列表”。
- 显示大号业务编号、业务类型、当前状态、风险、FCR 和融资笔数。
- 显示贸易主体、供应钢厂、品名和终端客户。
- 显示当前下一步。
- 显示来源摘要、最后来源更新时间、最后修改人和最后修改时间。

### 12.2 八个详情分区

页面顶部横向 01–08 导航与详情内容统一为：

1. 业务基本信息；
2. 合同明细；
3. 融资与银行还款；
4. 执行进度 / 船舶；
5. 单据 / 交单；
6. 客户回款；
7. 当前风险原因；
8. 数据异常与人工记录。

顶部横向导航随滚动显示当前章节，使用实心背景贴紧工作区顶部栏，并完整显示 01–08。点击章节只进行页内定位，不重新请求整个详情；较窄电脑端允许导航自身横向滚动，但页面级不得横向裁切。

### 12.3 子记录展示

- 合同、融资、还款、船舶、单据和回款必须逐条展示真实字段。
- 不得只显示“合同 3 条”“融资 1 条”等计数代替实际内容。
- 表格允许桌面端在表格容器内横向滚动，但章节标题、返回操作和顶部横向导航保持可见。
- 每条子记录显示来源、来源更新时间、修改人和修改时间等只读审计信息。
- 当前来源没有提供的字段显示“待来源回读”，不得生成演示值。

### 12.4 统一编辑态

- 有敏感操作权限的用户通过一个“编辑全部字段”入口进入页面级编辑态。
- 进入编辑态后，主卡和各子记录可编辑业务字段统一切换为输入控件。
- 系统计算字段、内部 ID、来源定位、来源更新时间、修改人和修改时间始终只读。
- 人工 FCR 在统一编辑态中勾选或取消，备注选填。
- 页面底部固定显示编辑备注、取消和保存。
- 保存时只提交发生变化的字段，但对用户表现为一次统一保存操作。
- 任一保存失败时不得退出编辑态，不得显示假成功；已经成功的变更必须回读后明确展示。
- 保存底层事实后必须重新计算状态、风险、完结日和下一步。

### 12.5 返回列表

从详情返回列表时必须恢复：

- 搜索字段和关键词；
- 全部筛选选择；
- 总览 / 本周关注重点；
- 当前页和每页条数；
- 列表滚动位置。

返回列表不得无条件重新加载并跳回第一页。

## 13. 性能修改方案

### 13.1 当前问题

当前列表接口先读取全部匹配业务，再针对每笔业务分别查询异常、来源、人工覆盖、六类子记录和人工子记录，完成全部业务卡组装后才排序、统计和分页。

这使页面只显示 20 条时，后台仍可能处理全部 100 余笔业务的完整子记录。当前查询数量近似随业务数量按 `16 × 业务数量 + 固定查询` 增长，是页面加载缓慢的主要原因。

### 13.2 推荐数据流

修改后的列表数据流固定为：

1. 数据库根据搜索、筛选和视图生成匹配业务集合；
2. 数据库按全部匹配业务计算顶部汇总；
3. 数据库按已确认规则完成排序；
4. 数据库执行分页并返回当前页业务 ID；
5. 后端只为当前页业务批量读取卡片所需子记录和聚合字段；
6. 接口返回汇总、当前页卡片、总数、页码、每页条数和来源状态；
7. 页面立即渲染当前页；
8. 用户打开详情时，再读取该笔业务的完整子记录、异常、来源和审计历史。

### 13.3 数据库职责

数据库负责：

- 搜索条件；
- 多选筛选；
- 总览 / 本周关注重点范围；
- 总业务数；
- 三项业务规模汇总；
- 六项运营指标；
- 风险和状态排序；
- 业务编号自然排序；
- 分页；
- 当前页业务卡所需的融资、回款、还款和执行摘要聚合。

数据库不得为了生成列表而返回全部合同、全部船舶、全部来源原文或全部审计历史。

### 13.4 接口返回范围

列表接口只返回：

- `summary`：全部匹配结果的汇总；
- `records`：当前页业务卡数据；
- `total`：全部匹配业务数；
- `page`；
- `page_size`；
- `sync_status`。

完整子记录只由单笔详情接口返回。列表接口中不得出现与业务卡无关的大字段、完整来源原文或完整审计数组。

### 13.5 批量查询要求

- 当前页需要六类子记录时，按当前页业务 ID 集合批量查询，不允许在循环中按每笔业务分别查询。
- 异常、来源元数据、人工覆盖和人工子记录同样按当前页业务 ID 批量查询。
- 列表接口 SQL 语句数量不得随全部匹配业务数量按每笔业务增长。
- 页大小为 20 时，不得加载未进入当前页的 80 或更多业务的完整子记录。
- 本周关注重点判断需要的字段应使用轻量聚合或数据库条件，不得以展开全部业务详情作为前提。

### 13.6 索引

在不改变业务数据的前提下，检查并补充以下查询路径的必要索引：

- 业务主表的有效状态、业务类型、状态、风险和业务编号；
- 合同、融资、船舶、单据、客户回款和银行还款的 `business_id`；
- 异常的 `business_id + status + anomaly_type`；
- 来源记录的业务键；
- 人工覆盖和人工子记录的 `business_id`、集合和有效状态。

索引变更必须先在 Local / Staging 验证执行计划和写入影响，不得直接进入 Production。

### 13.7 本期不采用永久汇总表

本期不新增永久汇总表或物化视图。原因是 WPS、邮件台账、人工覆盖和来源冲突会持续改变业务事实，永久缓存会增加刷新、失效和口径一致性风险。

如果未来业务规模增长到数据库聚合仍无法满足性能目标，再单独评估可重建汇总表、物化视图或增量缓存，并另行确认刷新时点、失效规则和回滚方案。

## 14. 加载、并发与错误处理

- 用户进入订单全流程页面后 200 毫秒内出现明确的列表加载状态。
- 搜索、筛选、视图或分页变化时保留当前页面结构，不整页闪白。
- 同一时刻只允许最后一次用户选择的请求回写页面。
- 较早请求即使更晚返回，也不得覆盖当前筛选结果。
- 请求结果必须与当前搜索、筛选、视图、页码和每页条数一致后才能渲染。
- 列表请求失败时保留上一次成功结果，并提示“本次条件未更新”。
- 详情请求失败时保留列表状态，显示可重试错误，不进入空白详情页。
- 无匹配业务、请求失败、权限不足和真实数量为 0 使用不同页面状态。
- 连续点击相同条件不得无限创建重复在途请求。

## 15. 业务编号规则与旧数据治理

### 15.1 权威编号规则

- 融资业务以 WPS 真实业务项次作为主编号，例如 `Y-2026-17`、`T-2026-1`。
- 过单业务以真实采购合同号作为主编号，例如 `B1YLD260501`。
- “XYZ-年份-数字”在本文中理解为真实来源编号格式族，不要求所有业务使用字面前缀 `XYZ`。
- 供应钢厂只作为业务字段显示，禁止参与拼接主编号。
- 来源文件名、页签、逻辑行号和数据库行号只用于追溯，禁止成为业务编号。
- 无真实业务编号的融资邮件记录不得建立临时主卡，应进入待匹配候选。
- 编号标准化只处理空格、大小写和横杠字符，不改变来源编号的业务含义。

### 15.2 新导入保护

- 新导入不得生成 `阿城-数字`、`北满-数字`、`承德-数字`、`东钢-数字`、`抚顺-数字`、`西林-数字` 等临时编号。
- 缺少权威编号时不得用钢厂、文件名、页签、行号或随机值补齐。
- 业务编号与现有主卡冲突时不得直接覆盖，应按真实合同和来源证据进入匹配或冲突处理。

### 15.3 Staging 旧编号治理

旧编号治理只在非 Production 环境按以下步骤执行：

1. 对 Staging 当前数据做可恢复备份或快照；
2. 识别符合旧临时编号特征的主卡；
3. 读取其已保存来源记录、采购合同、WPS 项次、来源版本和子记录归属；
4. 生成旧编号到权威编号的预览映射；
5. 唯一映射且不存在目标冲突时允许受控纠正；
6. 已存在同一权威编号主卡时，先比较合同、融资、船舶、单据、回款和审计记录，不能只改标题；
7. 多候选、证据不足或来源矛盾时停止自动处理，进入待确认；
8. 保留修改前编号、修改后编号、来源依据、操作人、操作时间和处理结果；
9. 治理后核对主卡数量、重复业务、全部子记录数量和人工审计数量；
10. 验收不通过时恢复治理前快照。

不得通过全表字符串替换或按钢厂顺序重新编号。
